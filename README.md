# Решись Авиа

Конкурсный проект турнира «Решись», направление «Технологии», задача «Динамическое ценообразование авиабилетов». Менеджер выбирает рейс и цену билета, чтобы увидеть прогноз спроса и число продаж с учётом вместимости.

## Возможности

- Пять маршрутов из Москвы, 155 комбинаций маршрута и даты с 1 июня по 1 июля 2026 года включительно.
- Медианный прогноз и девять сценариев при выбранной цене. На графике можно выбрать квантиль, сравнить спрос с числом мест и раскрыть таблицы.
- Регистрация, вход, выход и восстановление расчёта из личной истории последних 50 записей.
- Светлая, тёмная и системная темы, адаптивный интерфейс.

## Технологический стек

React 19, JavaScript/JSX и Vite формируют интерфейс. FastAPI, Pydantic и Uvicorn обслуживают API. Python читает CSV, SQLite хранит пользовательские данные, argon2-cffi хеширует пароли. Проверки используют pytest, HTTPX и Playwright. Для размещения подготовлены Docker Compose и конфигурация Nginx.

## Архитектура

Браузер обращается к одному адресу сайта. Локально Vite пересылает запросы `/api` в FastAPI, на сервере это делает Nginx. При запуске API проверяет CSV и загружает каталог в память. После входа браузер получает список маршрутов и доступных дат. Запрос `POST /api/forecast` передаёт поля `route`, `date` и `price`. Сервер вычисляет прогноз, сохраняет его для текущего пользователя и возвращает результат. Историю читает `GET /api/forecast/history`.

## Требования для запуска

Нужны Python 3.12, Node.js и npm. При аудите использованы Python 3.12.14, Node.js 24.21.0 и Vite 6.4.5. Для локальной демонстрации достаточно двух окон PowerShell. Для браузерных тестов нужен Chromium или установленный Google Chrome.

## Локальный запуск

Откройте оба окна в корне проекта. В первом создайте окружение и запустите API. Если Python установлен без команды `py`, для создания окружения используйте `python -m venv .venv` с Python 3.12.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
$env:COOKIE_SECURE = "false"
$env:AUTH_TRUSTED_ORIGINS = "http://127.0.0.1:5173"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Проверьте [состояние API](http://127.0.0.1:8000/api/health). Во втором окне выполните:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

Откройте [приложение](http://127.0.0.1:5173). Оставьте оба процесса запущенными на время демонстрации.

## Переменные окружения

Образец для Compose находится в [.env.example](.env.example). При прямом запуске задавайте значения через PowerShell перед стартом API.

| Параметр | Значение и назначение |
|---|---|
| COOKIE_SECURE | Локальный HTTP — false. В Compose закреплено true для HTTPS |
| AUTH_TRUSTED_ORIGINS | Разрешённые точные адреса сайтов со схемой и портом через запятую, без завершающего слеша. Для Secure-cookie укажите HTTPS |
| FORWARDED_ALLOW_IPS | В Compose обязателен адрес доверенного прокси, видимый контейнеру на TCP-соединении |
| AUTH_RATE_WINDOW_SECONDS | Окно подсчёта попыток входа и регистрации, 900 секунд |
| AUTH_LOGIN_IP_LIMIT / AUTH_LOGIN_EMAIL_LIMIT | Попытки входа за окно, 60 на IP и 20 на email |
| AUTH_REGISTER_IP_LIMIT / AUTH_REGISTER_EMAIL_LIMIT | Попытки регистрации за окно, 20 на IP и 5 на email |
| AUTH_RATE_MAX_KEYS | Максимум активных счётчиков в процессе, 10 000 |
| DATA_DIR / DB_PATH | По умолчанию backend/data и backend/app.sqlite3. В контейнере /app/data и /data/app.sqlite3 |
| API_PROXY_TARGET | Адрес API для прокси Vite, по умолчанию http://127.0.0.1:8000 |

## Использование приложения

1. Зарегистрируйтесь с email и паролем длиной от 8 до 128 символов. Регистрация сразу открывает сессию. При следующем входе используйте те же данные.
2. Выберите пару городов и одну из доступных дат. Введите цену в рублях и нажмите «Рассчитать прогноз». Цена должна быть конечным неотрицательным числом. Диапазон цен маршрута служит ориентиром.
3. Сравните медианный спрос, продажи и вместимость. Кнопки 10–90% выбирают сценарий. В режиме «Спрос покупателей» график ограничен снизу нулём. Переключите «Исходный расчёт модели», чтобы проверить линейную формулу ТЗ, включая отрицательные значения и исходную медиану. Продажи в обоих режимах ограничены нулём и числом мест. Раскройте таблицы для точных значений.
4. Выберите запись в «Истории поиска», чтобы восстановить параметры и сохранённый результат.

## Математическая модель

Для маршрута берутся базовая цена и коэффициент изменения спроса на один рубль. Для конкретной даты берутся число мест и базовый спрос каждого квантиля от 0,1 до 0,9 с шагом 0,1. Поля CSV с оптимальными ценами для этого расчёта не нужны.

```text
линейный спрос(q) = базовый спрос(q) − чувствительность × (цена − базовая цена)
спрос покупателей(q) = max(0, линейный спрос(q))
продажи(q) = min(число мест, спрос покупателей(q))
```

Медиана соответствует q = 0,5. API сохраняет исходную величину в demand и median_demand, физический спрос в customer_demand и median_customer_demand. Продажи имеют поля sales и median_sales. Вычисления сохраняют дробные значения. Спрос покупателей отображается до одного десятичного знака, исходный расчёт до двух. Денежные суммы показывают значимую дробную часть, включая копейки; цена перед отправкой не округляется. Для крайне малых цен используется научная запись. Квантили описывают уровни одного распределения. Границы q = 0,1 и q = 0,9 формируют номинальный центральный 80%-й интервал. При отсечении снизу несколько квантилей могут совпасть в нуле.

| Рейс | Цена | Мест | Исходная медиана | Спрос покупателей | Продажи по медиане |
|---|---:|---:|---:|---:|---:|
| Москва — Сочи, 01.06.2026 | 9 000 ₽ | 900 | 809 | 809 | 809 |
| Москва — Калининград, 19.06.2026 | 14 000 ₽ | 450 | −185,05 | 0 | 0 |

## Тестирование

Из корня проекта установите зависимости проверок и выполните:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
$env:PYTHONPATH = "backend"
.\.venv\Scripts\python.exe -m pytest backend/tests --basetemp=backend/.pytest-tmp
$env:RESHIS_PYTHON = (Resolve-Path .venv/Scripts/python.exe).Path
cd frontend
npm.cmd ci
npx.cmd playwright install chromium
npm.cmd run test:e2e
npm.cmd run build
cd ..
git diff --check
```

Для установленного Chrome можно пропустить установку Chromium и задать `$env:BROWSER_CHANNEL = "chrome"`. pytest использует отдельные базы во временном каталоге. Playwright запускает API на порту 18000 и Vite на 5179 с отдельной SQLite в frontend/test-results. Браузерные тесты используют копию CSV из backend/tests/fixtures/forecast. Серверные проверки также читают рабочий каталог данных.

После финальных доработок прошли 71 backend-тест и 19 Playwright-тестов, сборка frontend и `git diff --check`. Проверены оба режима графика, исходная отрицательная медиана, поздний ответ истории и цены 9000,49 ₽ и 9000,1234 ₽. Для общего IP браузерного тестового сервера установлена квота 100 регистраций за окно, поскольку сценарии используют один API-процесс. Рабочие значения лимитов не изменены. В установленной Starlette остаётся предупреждение об устаревшем BlockingPortal. Реальные HTTPS, Nginx и Docker-сеть требуют серверной проверки.

## Docker и развёртывание

1. Настройте DNS домена на сервер и выпустите TLS-сертификат. Для DuckDNS в deploy есть скрипты обновления и DNS-проверки Certbot. Храните DUCKDNS_DOMAIN и DUCKDNS_TOKEN в /etc/reshis/duckdns.env с доступом только владельца.
2. Скопируйте .env.example в .env в корне. Задайте публичный HTTPS-origin и точный IP прокси, с которого контейнер получает соединения. Проверьте подстановку через `docker compose config`. Запустите `docker compose up -d --build`. После изменения окружения пересоздайте контейнер.
3. Разместите содержимое frontend/dist в /var/www/reshis. Подставьте домен и пути сертификата в [шаблон Nginx](deploy/nginx.conf.example), включите конфигурацию, выполните `nginx -t` и перезагрузите Nginx. Порт API привязан к 127.0.0.1:8000. CSV входят в образ, именованный том sqlite_data хранит базу.
4. На сервере проверьте HTTPS, обновление сертификата, вход и выход, атрибуты cookie, разделение IP-квот через прокси и сохранность тестовой записи после пересоздания контейнера. Фактический статус проверок указан в [итоговом аудите](FINAL_AUDIT.md).

## Безопасность

Регистрация создаёт аккаунт и сессию одной транзакцией. Пароли хешируются Argon2id. SQLite хранит хеш токена сессии, сервер проверяет срок в восемь часов и отзывает токен при выходе. Cookie имеет HttpOnly и SameSite=Lax. История ограничена идентификатором текущего пользователя. Изменяющие запросы проходят проверку Origin. Для клиента без Origin требуется заголовок X-Requested-With со значением reshis, а при наличии Sec-Fetch-Site допустимо same-origin. Превышение лимита попыток возвращает 429 с Retry-After. История исправлений приведена в [AUTH_FIXES.md](AUTH_FIXES.md).

## Соответствие конкурсному ТЗ

Реализован вариант C раздела «Разработка»: форма отправляет маршрут, дату и цену в API, который возвращает места и прогноз продаж по формуле задания. Регистрация, авторизация и график доступны локально. Режим «Исходный расчёт модели» показывает на графике значение «желают» и медиану по формуле ТЗ. Для MOW-KGD на 19 июня при 14 000 ₽ графическая исходная медиана равна −185,05, спрос покупателей и продажи по медиане равны 0. Предыдущие замечания зафиксированы в [аудите](FINAL_AUDIT.md); он описывает состояние до финальных доработок. Публичный хостинг требует отдельного подтверждения. Критерии и состав сдачи приведены на страницах 12–14 [конкурсного задания](napravlenie-tekhnologii-zadacha-prodvinutogo-urovnia-59.pdf).

## Ограничения

Каталог ограничен рейсами исходного CSV. Приложение использует готовые прогнозы. Эмпирическая точность и фактическое покрытие интервала на продажах не проверены. Счётчики попыток хранятся в одном процессе и сбрасываются при перезапуске. Проверка конкурсных блоков «Бизнес и аналитика» и «Искусственный интеллект» выходит за рамки аудита приложения.
