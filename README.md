# Решись Авиа — прогноз продаж

## Быстрый запуск сервера

Чтобы запустить API-сервер локально в Windows, откройте PowerShell в папке проекта и выполните:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements.txt
$env:COOKIE_SECURE = "false"
$env:DB_PATH = "$PWD\backend\app.sqlite3"
python -m uvicorn app.main:app --app-dir backend --reload
```

Сервер будет доступен по адресу http://127.0.0.1:8000. Проверка работы API: http://127.0.0.1:8000/api/health. Оставьте это окно PowerShell открытым. Интерфейс запускается отдельно — см. раздел «Локальный запуск» ниже.

Веб-приложение для оценки спроса на авиабилеты по сезонному прогнозу. ML-модель не запускается: приложение использует опубликованные CSV из задания и пересчитывает девять квантилей для введённой цены.

## Возможности

- Регистрация, вход и выход; калькулятор требует активную сессию.
- Выбор одного из пяти маршрутов из Москвы и доступной даты.
- Расчёт медианного спроса и прогноза продаж с учётом вместимости.
- График девяти квантилей с отдельными отметками медианы и числа мест.
- Хранение аккаунтов и отзываемых сессий в SQLite.

## Данные

CSV лежат в backend/data/ и включены в проект:

- seasonal_forecast.csv — 155 строк по пяти маршрутам с 1 июня по 1 июля 2026 года.
- routes.csv — справочник маршрутов, базовые цены и чувствительность спроса к цене.

Источник резервных данных из задания: [seasonal_forecast.csv](https://gist.githubusercontent.com/Murkat-git/3ddc868889d3e0d37542d786c8b1aa74/raw/seasonal_forecast.csv) и [routes.csv](https://gist.githubusercontent.com/Murkat-git/3ddc868889d3e0d37542d786c8b1aa74/raw/a934b1220da2b20d7f3eb397a7459fe78ea168ef/routes.csv).

Для квантиля q backend вычисляет:

    спрос = q_base_demand - price_sensitivity * (цена - base_price)
    продажи = min(seats, max(0, спрос))

median_demand в API — неограниченный спрос сценария 0.5; median_sales ограничен вместимостью и нулём. Цена должна быть конечным числом не меньше нуля. Поля price_min и price_max показываются как ценовой ориентир, но не ограничивают расчёт.

## Локальный запуск

Нужны Python 3.12+ и Node.js 20+.

### Backend

В PowerShell из корня проекта:

    py -3.12 -m venv .venv
    .\.venv\Scripts\Activate.ps1
    python -m pip install -r backend/requirements.txt
    $env:COOKIE_SECURE = "false"
    $env:DB_PATH = "$PWD\backend\app.sqlite3"
    python -m uvicorn app.main:app --app-dir backend --reload

API будет доступен на http://127.0.0.1:8000; состояние сервиса — http://127.0.0.1:8000/api/health.

### Frontend

В другом окне PowerShell:

    cd frontend
    npm install
    npm run dev

Vite откроет адрес в терминале и проксирует запросы /api к локальному backend.

## Проверки

Из корня проекта:

    $env:PYTHONPATH = "backend"
    python -m pytest backend/tests --basetemp=backend/.pytest-tmp

Проверяются авторизация, точное сохранение пароля (включая пробелы), недопуск без сессии и после её истечения/выхода, вход после перезапуска, дубликат email, безопасные cookie, все 155 рейсов при четырёх ценах, нулевая вместимость, ошибки маршрута/даты/цены, включая NaN/Infinity, и некорректные CSV. Соединения SQLite закрываются после каждой операции.

Пароли не обрезаются и не нормализуются. Если аккаунт был создан старой версией с пробелами по краям пароля, та версия уже отбросила их: для такого аккаунта используется сохранённый пароль без этих пробелов.

Сборка frontend:

    cd frontend
    npm run build

Ручной браузерный сценарий: зарегистрироваться, выбрать маршрут и дату, рассчитать прогноз, сравнить медианную точку графика с карточкой спроса, выйти и убедиться, что калькулятор снова закрыт.

Автоматические браузерные проверки (из `frontend/`, после установки Python-зависимостей):

    npm ci
    npx playwright install chromium
    npm run test:e2e

Тесты сами поднимают изолированные API и frontend на портах 18000 и 5179. Python должен быть доступен как `python`; при необходимости в PowerShell задайте `$env:RESHIS_PYTHON = "$PWD\..\.venv\Scripts\python.exe"`. Для уже установленного Chrome вместо загрузки Chromium можно задать `$env:BROWSER_CHANNEL = "chrome"`. Тестовая база и снимки экрана находятся в `frontend/test-results/`, пользовательская база не используется.

Браузерные сценарии проверяют регистрацию и повторный вход, медиану и вместимость на графике, дробные значения, границы продаж, истечение сессии, отмену устаревшего расчёта при смене цены/даты/маршрута и вёрстку на экранах шириной 1440, 375 и 320 пикселей.

На графике ось Y показывает спрос в людях, ось X — уровень квантиля: вероятность спроса **не выше** значения соответствующей точки. Девять точек — квантили, а не девять независимых событий. Выделены медиана, диапазон центральных 80% прогноза и горизонтальная линия вместимости; оранжевая область показывает спрос выше числа мест. Квантиль можно выбрать мышью, касанием или кнопкой с клавиатуры: под графиком отображаются спрос и ограниченные вместимостью продажи. Также доступна таблица всех сценариев с той же точностью, что и карточки. Отрицательный спрос оставлен как результат формулы ТЗ; продажи в этом случае равны нулю. Даты в интерфейсе берутся из CSV. Изменение параметров отменяет предыдущий запрос, а ответ 401 возвращает пользователя к форме входа.

## Размещение на VDS

Конфигурация рассчитана на Ubuntu VDS:

1. Установить Docker Compose, Nginx, Certbot, curl и dnsutils.
2. Создать DuckDNS-поддомен и файл /etc/reshis/duckdns.env с переменными DUCKDNS_DOMAIN (имя без .duckdns.org) и DUCKDNS_TOKEN. Ограничить права файла: chmod 600.
3. Запустить deploy/duckdns-update.sh, чтобы направить поддомен на IP VDS.
4. Выпустить сертификат через DNS challenge:

       sudo certbot certonly --manual --preferred-challenges dns \
         --manual-auth-hook /opt/reshis/deploy/duckdns-auth.sh \
         --manual-cleanup-hook /opt/reshis/deploy/duckdns-cleanup.sh \
         --manual-public-ip-logging-ok --agree-tos -m YOUR_EMAIL \
         -d YOUR_SUBDOMAIN.duckdns.org

   При обновлении сертификата Certbot повторно вызывает эти hooks. Настроить и проверить таймер: systemctl enable --now certbot.timer, затем certbot renew --dry-run.
5. Скопировать содержимое frontend/dist/ в /var/www/reshis/. Скопировать deploy/nginx.conf.example в конфигурацию сайта Nginx и заменить YOUR_SUBDOMAIN.
6. В docker-compose.yml оставить COOKIE_SECURE: "true" и запустить из корня проекта docker compose up -d --build.
7. Проверить https://YOUR_SUBDOMAIN.duckdns.org, регистрацию, расчёт и /api/health.

SQLite хранится в именованном томе Compose и переживает пересоздание контейнера. CSV упакованы в образ API. Не помещать DuckDNS token, .env или базу с аккаунтами в публичный GitHub. Файлы скриптов DuckDNS следует скопировать на сервер в /opt/reshis/deploy/ и сделать исполняемыми.

Наличие этих конфигураций не означает, что приложение уже опубликовано. Публичный адрес, HTTPS, обновление сертификата и сохранность базы после перезапуска VDS нужно проверить на реальном сервере.

## API

- GET /api/health — статус приложения, публичный.
- POST /api/auth/register, POST /api/auth/login — принимают { "email": "...", "password": "..." }, создают сессию в HttpOnly cookie.
- POST /api/auth/logout — отзывает сессию и очищает cookie.
- GET /api/auth/me — текущий пользователь.
- GET /api/routes — список доступных маршрутов.
- GET /api/routes/{route}/dates — даты и число мест на рейсе.
- POST /api/forecast — принимает { "route": "MOW-AER", "date": "2026-06-01", "price": 9000 }; возвращает seats, median_demand, median_sales и девять записей scenarios с квантилем, спросом и продажами.
