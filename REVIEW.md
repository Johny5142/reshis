**Подтверждённые замечания, в порядке практической важности.**

1. **P2 — старый ответ истории перезаписывает новую историю.**

   Место: [App.jsx:272](C:/Users/cheni/Documents/ChatGPT/reshis/frontend/src/App.jsx:272), вызов после расчёта — строка 424. `refreshHistory` не отменяет предыдущий запрос и не проверяет, является ли ответ последним. Воспроизведение: задержать первоначальный GET истории с пустым списком; выполнить расчёт; дождаться нового GET с одной записью; разрешить старому ответу вернуться. История сначала содержит одну карточку, затем становится пустой. На сервере запись остаётся, после перезагрузки возвращается. Исправление: идентификатор последнего запроса либо AbortController с проверкой актуальности результата и состояния загрузки; отмена при размонтировании. Нужен регрессионный тест с изменённым порядком ответов.

2. **P3 — цена с копейками считается правильно, но отображается как другая цена.**

Разные расчёты могут выглядеть как расчёты при одной цене. Исправление: согласовать точность ввода, расчёта и вывода; для рублей и копеек показывать до двух знаков. Если выбираются только целые рубли, это ограничение должно одинаково действовать в UI и API.

**Логика и данные.**

В [data.py](C:/Users/cheni/Documents/ChatGPT/reshis/backend/app/data.py) для каждого квантиля применяется ровно формула ТЗ: `base_demand - price_sensitivity * (price - base_price)`. Медиана выбирается из сценария 0.5. Продажи ограничиваются `min(seats, max(0, demand))`. Для MOW-AER, 2026-06-01, 9000 ₽ получаются спрос 775, продажи 775, вместимость 900. При нулевой цене продажи ограничиваются 900; при достаточно высокой становятся нулевыми. Это проверено через API и браузер.

Правильно, что спрос не обрезается по вместимости: иначе график перестал бы показывать неудовлетворённый спрос. Отрицательный результат линейной формулы сохранён и объясняется в интерфейсе, продажи при этом нулевые. Поля оптимальных цен из CSV не подменяют расчёт при введённой пользователем цене. Собственная ML-модель для выбранного раздела не обязательна: ТЗ разрешает файл-заглушку.

Загрузка CSV проверяет структуру, обязательные поля, числа, даты, дубликаты, вместимость и порядок квантилей. Проверены все 155 рейсов при четырёх ценах. Цена за пределами `price_min`/`price_max` разрешена осознанно: ТЗ не устанавливает этот диапазон как ограничение. Даты июня–июля 2026 года соответствуют заданному набору, даже если текущая дата позже.

**Системный дизайн.**

Текущая схема: браузер → Nginx → статический React и `/api` FastAPI; backend держит проверенный CSV-каталог в памяти, а аккаунты, сессии и историю — в SQLite на постоянном томе. Для 155 строк данных и одного небольшого сервера это соразмерное решение. В коде разделены расчёт, БД, схемы запросов и проверка паролей. В SQL используются параметры, есть внешние ключи, индексы и WAL. Контейнер работает от отдельного пользователя, порт API в Compose привязан к loopback.

До публичной эксплуатации стоит закрыть следующие эксплуатационные вопросы; это не обнаруженные ошибки формулы:

- Ограничение частоты регистрации и входа отсутствует и в приложении, и в приложенном Nginx. Хеширование паролей требует ресурсов, а неограниченные попытки входа допускают перебор. Для публичного экземпляра нужен лимит запросов.
- Постоянный том сохраняет данные при пересоздании контейнера, но не заменяет резервное копирование. В проекте нет процедуры резервирования и проверки восстановления SQLite.
- Расчёт синхронно записывает историю до отправки ответа (`main.py:189`). Поэтому отказ записи в SQLite превращает даже уже вычисленный прогноз в ошибку. Следует явно решить, обязательна ли запись для успеха расчёта; для необязательной истории можно возвращать прогноз с понятным предупреждением о несохранении.
- CSV меняется только через перезапуск/пересборку. Для фиксированного задания это нормально. При будущих обновлениях понадобится версия данных, чтобы отличать сохранённые снимки истории от новых прогнозов.
- `App.jsx` содержит 818 строк и объединяет авторизацию, темы, форму, запросы и историю. При следующем изменении выделить Dashboard, AuthForm, HistoryPanel и отдельную логику запросов. Микросервисы, Redis и очереди этому объёму не нужны.
- Большинство бизнес-ответов API не имеют явных response-моделей, а TSX-компонент собирается без отдельной проверки типов. Это зоны улучшения контрактов и сопровождения, не препятствие текущей работе.

Публичный сервер, HTTPS, обновление сертификатов, резервное восстановление и нагрузка не проверялись. Из наличия файлов deploy нельзя сделать вывод, что эти свойства уже обеспечены.

Для завершения проекта не хватает явного соответствия «критерий ТЗ → реализация → проверка → доказательство на сдаче», последовательности этапов и приоритета хостинга. План в репозитории уже больше похож на отчёт о состоянии; противоречие по истории снижает его актуальность. Следует разделить реализованное, непроверенное и оставшиеся работы. Отсутствие восстановления пароля или подтверждения почты не является нарушением данного ТЗ.

Рекомендуемый порядок завершения: исправить гонку истории; согласовать точность цены и reduced motion; закрепить проверки истории в тестах; обновить план и README; разместить и проверить приложение либо подготовить полное видео с пониманием, что хостинг не будет засчитан; проверить комплект исходников, именование и сведения об использованных ИИ-инструментах.
