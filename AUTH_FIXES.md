# Исправления аутентификации «Решись Авиа»

Работа выполнена 14 ноября 2026 года по замечаниям предыдущего аудита. На начало работы Git содержал только неотслеживаемую папку .idea. Проверены реальные функции регистрации, входа, выхода, запросы frontend и схема SQLite. Требования раздела «Разработка» на страницах 12–14 ТЗ учтены по предыдущему аудиту. Регистрация и авторизация являются дополнительными функциями варианта C; меры безопасности ниже введены по текущему заданию пользователя.

## Исправления

| Замечание | Результат |
| --- | --- |
| B1 | register_user вставляет пользователя и первую сессию в одном соединении и транзакции. Cookie устанавливается после выхода из транзакции и успешного commit. Ошибка записи сессии вызывает rollback, повторная регистрация с тем же email проходит. |
| B4 | Только SQLITE_CONSTRAINT_UNIQUE для users.email превращается в DuplicateEmailError и HTTP 409. Другие ошибки SQLite дают безопасный 500, BUSY/LOCKED/CANTOPEN/IOERR/FULL/READONLY — 503 и Retry-After. Диагностика содержит только класс и числовой код ошибки. |
| B2 | Потокобезопасные ограничения по IP и нормализованному email, отдельно для login/register. IP ограничивается до валидации тела, email до хеширования или проверки пароля. Ответ 429 содержит Retry-After. Память ограничена числом активных ключей. |
| B5 | Один фиктивный Argon2id-хеш создаётся при загрузке процесса. Для неизвестного email выполняется проверка этого хеша. Ошибка для неизвестного email и неверного пароля одинакова. Параметры хеширования настоящих паролей сохранены. |
| B6 | Изменяющие запросы проверяют точный Origin. Без Origin требуется X-Requested-With: reshis и отсутствие cross-site/same-site Fetch Metadata. Заголовок автоматически добавляется общим клиентом frontend. Сохранены HttpOnly, SameSite=Lax и Secure при HTTPS. |
| B7 | Загрузка CSV и initialize_database перенесены в lifespan FastAPI. Импорт и создание объекта приложения не открывают SQLite. Схема не изменена, миграция не требуется. Повторная инициализация сохраняет аккаунты, сессии и историю. |

Все значения Origin проверяются по явно сформированному списку, включая login/register/logout и сохранение расчёта. Произвольный Origin нельзя разрешить через X-Requested-With. Запросы без Origin поддержаны для программных клиентов с этим заголовком. Сторонним сайтам CORS-доступ не открыт.

## Изменённые файлы

- backend/app/database.py — атомарная регистрация, отдельная ошибка занятого email, общая вставка сессии.
- backend/app/main.py — lifespan, обработчики SQLite, middleware Origin и IP, применение ограничений email.
- backend/app/security.py — фиктивный хеш и конфигурация точных доверенных Origin.
- backend/app/rate_limit.py — новый механизм ограничений.

- backend/tests/test_api.py — заголовки программного клиента и настройка HTTPS Origin для существующих тестов.
- frontend/src/api.js — служебный заголовок изменяющих запросов.
- frontend/tests/auth-security.spec.js — два самостоятельных браузерных сценария входа и выхода.
- frontend/playwright.config.js — доверенный Origin тестового frontend.
- docker-compose.yml — передача Origin и доверенных прокси в контейнер.

- AUTH_FIXES.md — этот отчёт.

Зависимости не добавлялись. Дизайн frontend, формулы прогноза и CSV не изменялись. Рабочая пользовательская SQLite не использовалась. Тесты создавали отдельные временные базы; браузер использовал отдельную тестовую базу и порты 18000/5179. Продакшен-инфраструктура не изменялась.

## Новые проверки

- Искусственный сбой записи сессии, отсутствие пользователя/сессии после отката, отсутствие Set-Cookie в ответе ошибки и успешная повторная регистрация.
- Конфликт email с другим регистром и отдельная обработка прочих IntegrityError.
- Шесть категорий недоступности SQLite, безопасные ответы и отсутствие текста SQL/секретов в проверенной диагностике.
- Ограничение IP до валидации запроса и игнорирование самостоятельно присланного X-Forwarded-For.
- Нормализация регистра email при ограничении входа и регистрации.
- Истечение окна и ограничение памяти таблицы счётчиков.
- Выполнение проверки хеша при неизвестном email и одинаковые внешние ошибки.
- Разрешённые локальные Origin, чужой Origin/порт/null, запрет обхода через заголовки.
- Отказ без Origin/служебного заголовка, отказ cross-site, успешный logout программного клиента.
- HTTPS Origin и атрибут Secure, отказ некорректной конфигурации Origin.
- Импорт и фабрика под запретом sqlite3.connect в отдельном процессе.
- Создание БД на lifespan, сохранение прежней схемы, входа, активной сессии и истории после перезапуска.
- Одновременная регистрация одного email — один аккаунт и одна сессия.
- Chrome в светлой и тёмной теме — регистрация, перезагрузка, выход, дубликат email, неверный пароль, повторный вход, возврат к форме после потери cookie.

## Переменные окружения

| Переменная | Значение по умолчанию / правило |
| --- | --- |
| AUTH_TRUSTED_ORIGINS | Точные origin через запятую, без пути и завершающего слеша. При локальном HTTP — localhost/127.0.0.1 на 5173 и 8000. При COOKIE_SECURE=true требуется явный HTTPS Origin. |
| AUTH_RATE_WINDOW_SECONDS | 900 секунд |
| AUTH_LOGIN_IP_LIMIT | 60 запросов входа за окно |
| AUTH_LOGIN_EMAIL_LIMIT | 20 запросов входа для email за окно |
| AUTH_REGISTER_IP_LIMIT | 20 запросов регистрации за окно |
| AUTH_REGISTER_EMAIL_LIMIT | 5 запросов регистрации для email за окно |
| AUTH_RATE_MAX_KEYS | 10000 активных счётчиков |
| FORWARDED_ALLOW_IPS | Настройка Uvicorn, явно передана в Compose. По умолчанию 127.0.0.1. Указать фактический доверенный адрес прокси, видимый API. |

COOKIE_SECURE уже существовала и сохранена. Числовые лимиты должны быть положительными целыми. В Compose значение AUTH_TRUSTED_ORIGINS требуется до запуска. Uvicorn при обычном запуске не загружает .env автоматически, значения задаются в окружении процесса.

## Ограничения

1. Лимиты хранятся в памяти одного процесса, общий Lock обеспечивает согласованность потоков. После перезапуска счётчики сбрасываются. Для нескольких workers/реплик требуется общее хранилище либо общий шлюз ограничений. Redis не добавлен.
2. Фиксированные окна допускают всплеск на границе окон. Считаются успешные и неуспешные попытки. Пользователи за одним NAT разделяют IP-лимит. При массовых попытках против одного email его лимит временно ограничит и владельца. Значения доступны для настройки.
3. Приложение использует request.client.host и не разбирает X-Forwarded-For. Uvicorn учитывает forwarded-заголовки только от доверенных прокси. Для Docker необходимо задать фактический адрес Nginx. Значение * не использовать. Публичное HTTPS-размещение и реальные адреса прокси в этой работе не проверялись.
4. Клиенты без Origin теперь должны передавать X-Requested-With: reshis. Если клиент присылает Origin, он должен входить в разрешённый список.
5. Фиктивная Argon2-проверка выравнивает основную вычислительную работу. Полное отсутствие временных различий не утверждается и сетевыми измерениями не подтверждалось.
6. При неудаче сети уже после commit клиент может не получить успешный ответ. Аккаунт в этом случае создан и доступен через обычный вход.
7. Инициализация некорректных CSV или недоступной БД при старте останавливает запуск приложения. HTTP-обработчик 503 относится к запросам работающего сервиса.
8. Версионирование схемы не вводилось, поскольку структура таблиц не изменилась. Перед будущими изменениями столбцов потребуется отдельная миграция.
